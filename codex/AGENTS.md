# 核心哲学

> **纯过程式 + POD 数据 + 可配置化 + 函数即目录 + 函数只做一件事 + 可观测 + 现代化 + 绝不过度设计——简单就是好。**

数据是数据，逻辑是逻辑；代码读起来像一份能层层下钻的提纲；关键路径都留下可观测的痕迹；能不抽象就不抽象，用当代语言最直接的表达。

## Environment

- OS: Mac
- Editor: Neovim
- Build tools: xmake (C++), uv (Python)
- Log monitoring: lnav
- Primary languages: Rust, C++23

## 铁则（Hard Rules）

- **每次回复完毕，只要本轮对任何文件有过增 / 删 / 改（新建、修改、删除、移动或重命名），必须在回复末尾明确列出涉及的文件路径。**
- **写程序之前，先确定好配置的定义。** 实现代码前必须列出每个配置项的名称、类型、默认值、取值范围、来源（环境变量 / 配置文件 / CLI）及其必须外置的理由。配置 schema 是先于实现确定的接口契约，不得边实现边追加。
- **大型分析任务必须限制最大内存。** 在支持 systemd 的 Linux 环境中使用 `systemd-run` 设置 `MemoryMax`；限制值根据主机可用内存、同期负载和预计峰值确定，为操作系统及其它进程预留安全空间，并记录实际限制值。

## Communication（沟通与表达）

- **图优先于长篇文字**：解释架构、流程、时序、状态转换、依赖关系、数据趋势和方案差异时，优先使用 Mermaid、ASCII 图、表格、PNG 或交互式 HTML；文字用于说明结论、约束和图中不便表达的细节。
- **选择最轻量且足够清晰的形式**：简单结构使用 ASCII，流程与依赖使用 Mermaid，重复维度使用表格，数据分布与趋势使用图表，需要动态探索时使用 HTML。
- **图必须自足且准确**：标题、节点、方向、图例和关键条件应足以支持独立理解；图与正文、代码和当前实现保持一致，不为装饰而作图。

## Code Style

### Paradigm（纯过程式 + POD）

- **数据与逻辑分离**：用 POD 结构体承载状态，用自由函数（Rust 自由 / 关联函数、C++ 自由函数）操作数据；避免继承、深层多态和将行为绑进对象。
- **POD 优先**：数据结构默认只包含字段和 derive；行为放在操作数据的函数中。
- **组合优于继承**：能用“数据 + 函数”表达的，不建立类层级。

### Function Design（函数即目录）

- **一个函数只做一件事**：函数内保持同一抽象层级，由一组自解释的命名调用组成；读函数名即可了解意图，需要细节时再逐层下钻。
- **行数是结果，不是判据**：编排函数理想上不超过 5 行，多数函数不超过 15–20 行；超过 40 行时重点检查是否混入多个职责或抽象层级，不为压缩行数制造共享隐式状态的碎片函数。
- **区分可读性抽取与通用抽象**：为压平抽象层级而抽函数，即使只调用一次也可以；为复用而建立泛型、trait、接口或通用层，应等共性真正稳定。

### Simplicity（简单，不要过度设计）

- **选择能正确完成需求的最简单方案**：优先显式、扁平、易修改的代码，不为假想的未来需求预留开关、扩展点或抽象层。
- **遵循 YAGNI 与三次法则**：两段相似代码可以暂时重复；等共性至少三次出现并稳定后再抽象。若通用函数开始堆积 bool 参数和特例分支，先内联回显式实现。
- **现代化服务于简单**：只在让代码更直接、更安全或更高效时使用新语法和技巧，不为展示技术增加复杂度。

### Configuration（配置）

- **配置只表达环境差异**：因部署或运维而变的密钥、endpoint、超时、重试、并发度、日志级别和路径应外置；因需求或业务逻辑而变的规则应留在代码中。
- **禁止 soft-coding**：不把业务规则塞进 YAML，不为“万一以后要换”增加配置项。每个配置项都将决定延迟到运行期，必须有明确的部署或运维需求。

### Error Handling（适度防御，区分可恢复性）

- **可恢复性取决于当前层级**：只有当前层拥有明确、有限，且能保持核心语义与结果可信的恢复动作时，错误才是可恢复的；否则保留原因并向上传播。
- **可恢复错误应显式恢复**：使用契约中已定义的默认值、有限重试、跳过可选数据、关闭非关键功能或切换到既定备用路径；恢复后向调用方显式报告降级状态。
- **恢复必须有边界**：禁止无限重试、递归降级、无依据的默认值和静默容错；恢复不得改变核心业务语义、隐藏数据损坏或生成不可信结果。
- **不可恢复错误应停止最小必要作用域**：终止当前记录、请求、任务、事务或组件，清理资源，必要时回滚或补偿已产生的副作用，并向上传播完整错误链；不默认终止整个进程。
- **仅在进程无法继续可信运行时退出**：核心不变量被破坏、全局状态已损坏或错误无法安全隔离时，才使用 panic、abort 或进程退出。
- **防御必须与实际风险相称**：对外部输入、权限与安全边界、持久化数据、协议和不可逆操作严格校验；不重复校验已由类型、构造流程或上游逻辑保证的内部不变量，不为纯理论异常路径牺牲可用性。

### Observability（可观测）

- **关键点必须留痕**：函数入口 / 出口（`DEBUG`）、所有错误分支、外部 I/O、关键业务决策和降级恢复都应留下日志或 span。
- **延迟必须可观测**：对外部 I/O 和关键业务函数记录耗时，慢路径应能直接从日志中定位。
- **日志必须 actionable**：级别统一使用大写的 `ERROR` / `WARN` / `INFO` / `DEBUG` / `TRACE`；使用稳定、语义明确的 `key=value` 字段记录相关输入、系统状态、错误原因、恢复动作与影响，同时保留简短的人类可读消息。
- **同一错误只在负责处理的边界记录一次**：中间层只补充上下文并继续传播，避免重复刷屏。
- **语言约定**：Rust 使用 `tracing`，非平凡函数标注 `#[instrument(err)]`；C++ 使用 Quill 的异步日志与 scoped timer，并通过 `QUILL_COMPILE_ACTIVE_LOG_LEVEL` 做编译期日志过滤。

### Modern by Default（现代化）

- **使用当代语言最直接的表达**：C++23 优先 concepts、ranges、`std::expected`、`std::format` 和结构化绑定；倾向编译期驱动开发，库尽量 header-only。
- **Rust 使用惯用表达**：善用类型系统、`?`、迭代器适配器、derive 和零成本抽象。

### Naming（命名）

- **默认拼写全名**：只使用领域内无歧义的通用缩写，如 `id` / `url` / `ctx` / `cfg` / `req` / `db`，并在全代码库保持一致；不自创缩写。
- **描述机制，不描述当前部署实例**：命名和注释使用稳定的角色（如 `upstream_relay`），不写死 IP、主机名、区域、端口或具体链路；会随部署变化的实例值属于配置。

### Comments（注释）

- **注释解释代码无法自证的信息**：记录意图、约束、不变量、边界条件、单位、所有权、并发要求和反直觉实现的原因；不逐句复述代码。
- **注释只描述当前实现**：删除过期注释、被注释掉的代码和无助于理解当前实现的历史沿革；修改代码时同步核对附近注释。

### Testing（测试）

- **测试从需求出发**：先明确需求、验收条件和业务不变量，再设计正常路径、边界条件、非法输入、错误路径和相关状态转换；不从实现分支或覆盖率数字倒推测试。
- **测试可观察行为**：断言输入输出、状态变化、错误语义和必要副作用；除非调用顺序本身就是需求，不断言私有函数、内部步骤或 mock 调用细节。
- **一个测试表达一个行为**：名称直接说明“在什么条件下，应产生什么结果”，失败时无需阅读实现即可判断哪条需求被破坏。
- **选择最低但正确的测试层级**：确定的局部规则用单元测试；模块协作、外部 I/O、协议和完整业务流程用集成或系统测试。只在隔离外部系统、时间、随机性或昂贵 I/O 时使用 test double。
- **缺陷修复要补需求回归测试**：名称和断言描述被破坏的需求及触发条件，不复刻缺陷发生时的内部代码路径。
- **覆盖率是诊断信号，不是完成标准**：用它发现遗漏，不为提高数字编写没有行为价值的断言；完成的判据是需求风险得到验证。

## Project Documentation（项目文档）

### File Organization（文件组织）

- **每个项目都必须有文件组织说明**：用带职责注释的 ASCII 目录树展示实际存在的主要源码目录、关键入口和稳定模块边界，让读者无需遍历代码即可建立整体印象。
- **只展开表达架构所需的深度**：通常为 2–3 层；不穷举普通文件，不列构建产物、缓存、生成代码和第三方依赖。大型项目在顶层给出整体地图，模块细节在就近文档中下钻。
- **目录说明必须与当前结构同步**：只描述已存在的结构，不写规划中的目录；新增、删除、移动目录或改变模块职责时必须同步更新。

### Reports（报告）

- **面向有相关基础知识的新人**：不从领域常识讲起，也不假设读者了解项目历史、内部架构、专有术语、隐含约定和当前上下文；非常识概念首次出现时用一句话解释。
- **摘要先行，正文自足**：开头先给出结论、关键依据、影响和建议行动；正文按“背景 / 触发条件 → 机制 → 结果 → 影响”组织，不依赖未说明的口头背景或历史记忆。
- **区分事实、推断与建议**：重要结论就近给出数据来源、代码位置或复现方式；证据不足时明确标注不确定性，不把推断写成事实。
- **可视化服务于关系**：流程或时序用流程图，目录与层级用树，字段映射、方案比较和重复维度用表格；只在比连续文字更易理解时使用。
- **旁注和附录只承载补充信息**：Markdown 旁注统一使用 `> 旁注：...`；关键结论、必要前提和风险不得只放在旁注或附录中。附录用于原始日志、完整配置、详细数据、长篇复现过程和次要分析。
