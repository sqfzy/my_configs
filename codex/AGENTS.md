# 核心哲学

> **纯过程式 + POD 数据 + 可配置化 + 函数即目录 + 函数只做一件事 + 可观测 + 现代化 + 绝不过度设计——简单就是好。**

一句话：**数据是数据、逻辑是逻辑；代码读起来像一份能层层下钻的提纲；关键路径都留下可观测的痕迹；能不抽象就不抽象，用当代语言最直接的表达。** 下面各节都是这句话的展开。

## Environment
- OS: Mac
- Editor: Neovim
- Build tools: xmake (C++), uv (Python)
- Log monitoring: lnav
- Primary languages: Rust, C++23

## 铁则（Hard Rules）
- **每次回复完毕，只要本轮对任何文件有过增 / 删 / 改（新建、修改、删除、移动或重命名），必须在回复末尾明确列出涉及的文件路径。**
- **写程序之前，先确定好配置的定义。** 动手写实现代码前，必须先把配置项定义清楚——列出每一项：名称、类型、默认值、取值范围、来源（环境变量 / 配置文件 / CLI）、以及"它为何是配置而非硬编码"（判据见 Configuration 节：因部署 / 运维而变 → 配置）。配置的形状（schema）是接口契约，必须先于实现敲定，不能边写边拍脑袋加。
- **大型分析任务必须限制最大内存。** 在支持 systemd 的 Linux 环境运行大型分析程序时，使用 `systemd-run` 设置 `MemoryMax`，不得无上限运行；限制值根据主机可用内存、同期负载和任务预计峰值确定，既为任务保留合理余量，也必须为操作系统及其它进程预留安全空间，并在执行记录中注明实际限制值。

## Project Documentation（项目文档）

### File Organization（文件组织）
- **每个项目必须包含文件组织目录说明**，让读者无需遍历代码即可快速建立项目的初步印象
- 使用带职责注释的 ASCII 目录树，展示实际存在的主要源码目录、关键入口与稳定的模块边界；每个重要节点用一句话说明“负责什么”
- 目录树只展开到足以表达架构的深度，通常为 2～3 层；不穷举普通文件，不列构建产物、缓存、生成代码或第三方依赖目录
- 目录说明只描述当前真实结构，不记录规划中的结构；新增、删除、移动目录或改变模块职责时，必须同步更新
- 项目较大时，只在顶层说明中给出整体地图，更细的结构在对应模块的就近文档中继续下钻，避免顶层文档膨胀

### Reports（报告）
- **将读者视为有相关基础知识的新人**：默认读者了解所属领域的基础概念，但不了解本项目的历史背景、内部架构、专有术语、隐含约定和当前上下文；不从常识讲起，也不假设读者已经参与过相关工作
- **摘要先行**：开头先给出结论、关键依据、影响与建议行动，让读者无需通读即可掌握重点；详细证据、原始数据、复现步骤和补充材料可放在文末附录
- **上下文自足**：正文必须包含足以独立理解结论的背景和因果关系，按“背景 / 触发条件 → 机制 → 结果 → 影响”组织；不能依赖未说明的口头背景或历史记忆
- **解释非常识概念**：面向目标读者并非一眼可懂的术语、缩写、指标和项目专有名词，在首次出现时用一句话解释；常识性概念不重复科普，避免打断主线
- **区分事实、推断与建议**：明确哪些内容来自代码、日志、测试或配置，哪些是基于证据的推断，哪些是后续建议；不把不确定判断写成既定事实
- **证据可追溯**：重要结论应就近给出对应证据、数据来源、代码位置或复现方式；无法验证或证据不足时明确说明不确定性
- **旁注服务于主线**：使用旁注补充有价值但非主线的信息，例如术语背景、特殊边界或实现细节；关键结论、必要前提和风险不得只放在旁注中。Markdown 旁注统一使用 `> 旁注：...`，不引入复杂的提示框类型体系
- **优先选择适合关系的表达形式**：流程或时序使用流程图，目录与层级使用树形结构，字段映射、方案比较和重复维度使用表格；只有在比连续文字更容易理解时才使用可视化
- **正文保持自足，附录承载细节**：读者不查看附录也应能理解结论及其主要依据；附录用于原始日志、完整配置、详细数据、长篇复现过程和次要分析

## Code Style

### Paradigm（范式）——纯过程式 + POD
- **数据与逻辑分离**：用 POD 结构体承载状态，用自由函数（Rust 自由/关联函数、C++ 自由函数）操作它；避免 OOP 仪式（继承、深层多态、把行为绑进对象）。这是刻意的过程式选择，不是"贫血模型"反模式
- **POD 优先**：数据结构默认就是"只有字段、无自定义语义"的纯数据（C++ aggregate/POD、Rust `#[derive]` 的普通 struct）；行为放在操作数据的函数里，而非塞进对象
- **组合优于继承**：能用「数据 + 函数」表达的，就不要用类层级

### Function Design（函数即目录 + 只做一件事）
- **「函数即目录」**：每个函数只在同一抽象层级上做一件事，由一串自解释的命名调用组成，让人能自顶向下逐层下钻——读函数名即懂意图，要细节再进下一层
- 综合 Compose Method（组合方法）+ SLAP（单一抽象层级原则）+ Clean Code 的 Do One Thing & Stepdown Rule + Extract Function / SRP：代码读起来应像一份能层层展开的提纲
- **行数是结果而非判据**：编排函数理想 ≤5 行，多数函数舒适上限 ≤15~20 行，>40 行基本确定违反 SLAP。但真正的拆分信号是"同一函数混入了两种抽象高度的词汇"或"做了多件事"——超行数只是去查这个病因的提示。反之也别为压行数硬拆出只能连在一起读、共享隐式状态的碎片
- **区分两种"抽"**：为"读得懂 / 压平抽象层级"而抽函数——单次调用也尽管抽（本地、廉价、可逆）；为"将来复用 / 消除重复"而抽通用抽象——延后到共性稳定（YAGNI）

### 绝不过度设计（扁平化，不过早抽象）
- **简单就是好**：favor the simplest solution that works；resist over-engineering；prefer explicit over clever
- **扁平化代码，不要过早抽象**：遵循 YAGNI + Rule of Three（三次法则）+ "宁可重复，勿要错误的抽象"（Sandi Metz）。错误抽象的代价（特例分支、flag 参数、被 N 处绑死）远高于重复（线性、显式、可逆）。需要泛型 / trait / 接口 / 配置驱动的"万能函数"时，等共性出现第三次、真正稳定后再抽；发现抽错了，先内联回重复再重新提炼
- 警惕伪装成 DRY 的过早抽象：看到两段相似代码就急着抽一个带多个 bool 参数的"共用函数"，那不是 DRY，是过早抽象

### Configuration（可配置化）
- **可配置化**：把随环境 / 部署 / 运维而变的量外置为配置（密钥、endpoint、超时、重试、并发度、日志级别、路径），代码里不写死
- **判据**：因部署 / 运维而变 → 配置；因需求 / 业务逻辑而变 → 代码。配置表达**环境差异**，不表达**业务逻辑**（避免 soft-coding：把业务规则塞进 YAML 反而更难读、更难改、逻辑两处散落）
- 配置项也受 YAGNI + 三次法则约束：别为"万一以后要换"预留开关。每个配置项都是一次延迟到运行期、绕过编译器检查、且与其它开关组合爆炸的决定

### Defensive Programming（适度防御，优先保证可用性）
- **防御性编程必须与实际风险相称**：只针对有明确需求、真实故障记录或合理威胁模型的风险增加校验与保护；不要为纯理论上的异常路径堆砌检查、状态和抽象
- **关键边界严格，内部路径简洁**：对外部输入、权限与安全边界、持久化数据、协议边界和不可逆操作严格校验；对进程内部已经由类型、构造流程或上游逻辑保证的不变量，不重复防御
- **可恢复问题不得轻易阻断主流程**：非关键配置缺失、可忽略数据异常、辅助功能失败等情况，优先采用明确的默认值、降级、跳过或有限重试，并记录带上下文的 `WARN`
- **仅在继续运行会造成更大损害时快速失败**：可能导致数据损坏、安全问题、错误外部副作用或结果不可置信时，应立即终止相关操作并返回清晰错误；不要把 fail-fast 泛化到所有异常
- **禁止静默容错**：降级或忽略异常必须保持可观测，日志说明触发条件、采用的替代行为及影响；不得吞掉错误后假装正常完成
- **避免“为了安全而不可用”**：新增保护逻辑时必须同时评估误拒绝、部署兼容性和运行连续性；若保护造成的可用性风险高于其防范的实际风险，应采用更宽容、直接的实现

### Observability（可观测——关键点必留痕）
- **所有关键点都有日志**，尤其是**延迟**和**关键业务函数**：函数入口/出口（DEBUG）、所有 error 分支、外部 I/O、关键业务决策点
- **延迟可观测**：对外部 I/O、关键业务函数记录耗时（Rust `#[instrument]` span / C++ scoped timer + Quill），慢路径要能从日志直接看出耗时，而非靠猜
- **日志格式**：日志级别统一使用大写的 `ERROR` / `WARN` / `INFO` / `DEBUG` / `TRACE`，各司其职；事件上下文使用结构化的 `key=value` 字段，key 保持稳定、语义明确且全项目一致，同时保留简短的人类可读消息，不把关键上下文只埋在自然语言中
- **日志必须 actionable**：带上相关上下文——变量值、函数入参、系统状态——而不是只写 "error occurred"
- **Rust**：用 `tracing`；非平凡函数标注 `#[instrument(err)]`，关键业务函数带 span 以观测延迟
- **C++**：用 Quill（高性能异步日志，热路径仅拷贝参数、格式化与 I/O 交由后台线程），配合 `QUILL_COMPILE_ACTIVE_LOG_LEVEL` 做编译期日志过滤

### 现代化（Modern by default）
- **用当代语言最直接的表达**，别写遗留风格
- **C++23**：优先 concepts、ranges、`std::expected`、`std::format`、结构化绑定等，替代 legacy 模式；倾向编译期驱动开发（常量求值、泛型编程），尽早暴露错误、提升性能；C++ 库尽量 header-only
- **Rust**：善用类型系统、`?`、迭代器适配器、`derive`、零成本抽象等惯用法
- 现代化服务于"简单"，不是炫技：只在让代码更直接、更安全、更快时采用

### Naming
- **默认拼全名**：只允许领域内人人秒懂、无歧义的通用缩写（`id` / `url` / `ctx` / `cfg` / `req` / `db` 等），且一旦采用就全代码库一致——绝不自创只有自己当下懂的简写
- **描述「机制」，不描述「当前部署的具体实例」**：注释、命名、文档只说明"这是什么角色 / 起什么作用 / 怎么运作"，不写死当下这一次部署的具体值（IP、主机名、区域、端口、某台机器、某条链路）。命名按角色（`upstream_relay` 而非 `box_52_199`）；具体实例值属于配置（见 Configuration 节），不是标识符或注释。判据：会随部署变的具体值 → 配置；不随部署变的角色/机制 → 代码与文字

### Comments（注释）
- **从人读代码的视角写必要且易读的注释**：注释的价值是降低理解成本，解释代码本身无法清楚表达的意图、约束、不变量、边界条件、单位、所有权、并发要求，以及反直觉实现背后的原因
- 优先通过清晰的命名、数据结构和函数拆分让代码自解释；不要用注释逐句复述代码在做什么，也不要给显而易见的代码加旁白
- 注释只描述当前实现仍然成立的信息；删除过期注释、被注释掉的代码，以及对理解当前代码无帮助的历史沿革。需要保留的变更原因放在版本历史或设计文档中
- 修改代码时同步检查附近注释；无法确认仍然准确的注释不得原样保留

### Testing（测试）
- **测试从需求出发**：先明确需求、验收条件和业务不变量，再据此设计测试场景；不以函数结构、实现分支或覆盖率数字作为测试设计的起点
- **测试可观察行为，而非内部实现**：断言输入输出、状态变化、错误语义和必要副作用；除非调用顺序本身就是需求，否则不要断言私有函数、内部步骤或 mock 调用细节
- **覆盖有需求依据的场景**：至少考虑正常路径、边界条件、非法输入、错误路径和相关状态转换；不为脱离真实需求的假想场景堆积测试
- **一个测试表达一个行为**：测试名称应直接说明“在什么条件下，应产生什么结果”；测试失败时，读者无需阅读实现即可知道哪条需求被破坏
- **选择最低但正确的测试层级**：局部且确定性的业务规则使用单元测试；模块协作、外部 I/O、协议和完整业务流程使用集成或系统测试，不把所有需求强行塞进单元测试
- **减少实现耦合**：优先使用真实的 POD 输入与返回结果；只在隔离外部系统、时间、随机性或昂贵 I/O 时使用 test double，不为方便测试而模拟内部实现
- **缺陷修复先还原需求**：为缺陷补充回归测试时，测试名称和断言描述被破坏的需求及触发条件，而不是复刻缺陷发生时的内部代码路径
- **覆盖率是诊断信号，不是完成标准**：使用覆盖率发现遗漏，但不为提高数字编写没有行为价值的断言；测试完成的判据是需求风险得到验证
